# SDD 规范驱动开发集成方案

## 1. 定位

本方案用于在根仓库统一引入 SDD（Specification-Driven Development，规范驱动开发）研发流程。根目录负责承载统一的需求规格、计划、任务拆分、跨子模块协同和流程说明；各子项目继续保留自身的 `AGENTS.md`、README、验证命令、技术栈约束和交付规则。

本文件只描述团队研发流程，不执行 `specify init`，不初始化工具目录，不提交 Spec Kit 或 Superpowers 插件产物，也不修改任何业务代码。

目标是让后续需求先形成可评审、可验收、可追踪的规格，再进入实现；同时避免把所有子模块强行套成同一套工程细节。

## 2. 为什么放在根目录

当前仓库是 AI Integration Platform 与数智底座相关工程的聚合入口，通过 Git submodule 组织后端、前端、数据服务、元数据服务和调度平台。统一研发流程放在根目录，可以作为跨子模块需求的唯一入口，避免需求、计划和验收标准散落在多个子项目中。

根目录适合承载以下内容：

- 跨子模块或跨团队的统一需求规格。
- 需求到计划、任务、验证和交付的统一流程。
- 子模块边界、提交边界和根仓库子模块指针管理规则。
- 对破坏性操作、高风险变更和外部系统影响的统一约束。

子项目仍负责承载以下内容：

- 具体代码实现、模块内测试和构建脚本。
- 子项目自己的 `AGENTS.md`、README、docs 索引和工程规范。
- 子项目特有的 API、数据库、前端、MCP、Dify、部署或运行时约束。

## 3. Spec Kit 和 Superpowers 分工

Spec Kit 负责 SDD 主流程，重点是把需求先变成明确的规格、计划和任务：

- `constitution`: 固化团队级工程原则和不可违反的约束。
- `specify`: 描述用户目标、场景、验收标准和非目标。
- `clarify`: 澄清高影响的不确定性，避免实现阶段再补业务决策。
- `plan`: 将规格转为可实施方案，明确模块影响、接口、数据、兼容性和风险。
- `tasks`: 将方案拆成可验证、可分配、可追踪的任务。
- `analyze`: 检查规格、计划和任务之间是否一致、完整、无明显冲突。

Superpowers 负责 AI 开发节奏和代理协作方式，重点是让开发过程更轻量、更连续：

- 需求早期用 brainstorming 帮助收敛意图。
- 实现前用 planning 明确切片和验证路径。
- 实现中用 TDD 工作流推动先验收、再编码、再验证。
- 合并前用 review 和 finish 流程检查风险、遗漏和交付边界。

两者关系是：Spec Kit 管“要做什么、为什么、验收什么”，Superpowers 管“AI 代理如何高质量地推进开发过程”。

## 4. 推荐目录结构

首次正式落地时，建议在根目录初始化一套 Spec Kit 结构：

```text
.
├── .specify/
│   ├── memory/
│   │   └── constitution.md
│   └── templates/
│       └── overrides/
├── specs/
│   └── <feature-id>/
│       ├── spec.md
│       ├── plan.md
│       └── tasks.md
├── SDD_WORKFLOW.md
└── <submodules>/
```

推荐原则：

- 根目录只初始化一套 `.specify/` 和 `specs/`，作为统一 SDD 入口。
- 子模块默认不重复初始化完整 Spec Kit，避免出现多套互相割裂的规格入口。
- 子模块如需补充特殊规则，优先写入该子模块的 `AGENTS.md`、README 或 docs 索引，再由根级规格引用。
- 根级 `specs/<feature-id>/` 应明确列出命中的子模块、实现边界和验证方式。

## 5. 标准工作流

### 单子项目需求

1. 在根目录创建 `specs/<feature-id>/`，规格中明确目标子模块。
2. 读取根目录 README、本文件，以及目标子模块最近的 `AGENTS.md`、README、docs 索引。
3. 通过 Spec Kit 产出或维护 `spec.md`、`plan.md`、`tasks.md`。
4. 进入目标子模块实施任务，遵守该子模块自己的工程规则和验证命令。
5. 在子模块内提交业务代码；根仓库只在需要固定新的子模块提交时提交指针变化。

### 跨子项目需求

1. 根级 `spec.md` 作为唯一需求源，统一描述业务目标、用户场景、验收标准和非目标。
2. 根级 `plan.md` 按子模块拆分实现策略，明确每个子模块的接口、数据、兼容性和风险。
3. 根级 `tasks.md` 按子模块拆分任务，标注目标仓库、验证命令和提交边界。
4. 每个子模块独立实现、独立验证、独立提交。
5. 最后在根仓库提交子模块指针变化和根级规格文档更新。

### 高风险需求

涉及接口、数据库、权限、安全、部署、消息、定时任务、外部集成、MCP、Dify 或真实用户数据时，必须先完成规格和计划评审，再进入实现。

高风险需求的计划必须写清：

- 精确影响的子模块、接口、表、配置、任务或外部资源。
- 是否涉及租户隔离、权限边界、敏感数据或真实外部系统写入。
- 是否需要数据库脚本、迁移、回滚、灰度、监控或人工确认。
- 验证命令、验证环境和不可验证路径的剩余风险。

## 6. 子项目规则继承

根级 SDD 流程不覆盖子项目规则。命中某个子模块时，必须遵守以下优先级：

1. 用户当前明确要求。
2. 根目录统一流程和破坏性操作禁令。
3. 目标子模块最近的 `AGENTS.md`、README、CONTRIBUTING、docs 索引和任务文档。
4. 子模块现有代码、测试、脚本、CI 和依赖管理方式。
5. 根级 Spec Kit 规格、计划和任务。

当根级规格与子项目规则冲突时，默认选择更安全、影响面更小、可验证、可回滚的方案；如果冲突会改变业务边界或交付方式，必须先更新规格或记录决策，再继续实现。

## 7. 高风险变更要求

默认禁止删除、清空、重置、覆盖、重建、强制 Git、生产操作、真实外部系统写入、不可逆迁移、批量改数据或影响用户数据的操作。

确实必须执行高风险操作时，必须先在规格或计划中写清：

- 精确对象和路径、表、分支或资源。
- 必要性和非破坏性替代方案。
- 影响范围。
- 备份、回滚、恢复和验证方式。
- 需要谁确认，以及确认后如何记录。

未获得明确确认前，不执行高风险操作。普通 `git add`、`git commit`、普通 `git push` 不属于破坏性操作，但仍必须先检查 `git status`，只处理当前任务相关文件。

## 8. 提交和验证策略

根仓库和子模块的提交边界必须清晰：

- 只改根级流程文档、`.specify/` 或 `specs/` 时，在根仓库提交。
- 修改子模块业务代码时，在对应子模块提交。
- 根仓库只有在需要固定新的子模块提交时，才提交子模块指针变化。
- 提交前必须分别查看根仓库和相关子模块的 `git status`，避免混入无关改动。

验证策略：

- 根级文档变更：至少运行轻量文本检查，例如 `rg` 检查关键术语和链接。
- 后端业务变更：按目标子模块 Maven 命令执行测试或编译。
- 前端业务变更：按目标子模块 npm/yarn 命令执行 lint、test 或 build。
- 数据库脚本：默认只归档和静态检查；执行 DDL、DML、迁移、回填或清理前必须单独确认。
- 未运行的验证必须说明原因和剩余风险，不把未验证说成已验证。

## 9. 首次落地步骤

建议首次正式落地按以下顺序执行：

1. 确认根仓库和各相关子模块没有会被混入的无关改动。
2. 在根目录安装或确认 Spec Kit CLI 可用。
3. 在根目录执行初始化命令：

   ```bash
   specify init --here --integration codex --integration-options="--skills" --ignore-agent-tools
   ```

4. 编写根级 `.specify/memory/constitution.md`，纳入根仓库职责、子模块规则继承、破坏性操作禁令、提交边界和验证要求。
5. 定制根级模板覆盖，要求规格和计划必须声明命中的子模块、接口/数据/权限影响、验证命令和提交边界。
6. 创建一个 smoke spec，例如 `specs/001-root-sdd-smoke/`，只验证规格、计划和任务格式，不改业务代码。
7. 运行轻量检查：

   ```bash
   find .specify specs -maxdepth 3 -type f | sort
   rg "Spec Kit|Superpowers|SDD|子模块|AGENTS|验证|提交" .specify specs SDD_WORKFLOW.md README.md
   ```

8. 检查 `git status`，只暂存根级流程文件和本次新增的 Spec Kit 结构。
9. 提交根级流程变更；如果未修改子模块提交，不提交子模块指针。
